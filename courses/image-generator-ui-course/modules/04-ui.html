The LEGO Box

Nobody wrote the colour yellow anywhere near the upload box. Here is how the glow gets there — through four layers of indirection, every one of them earning its keep.

Drag a photo over the box. It glows yellow.

Last module we watched the app hand a written brief to a rented artist. Now turn around and look at the dashboard the app built around that engine — the panel, the buttons, the glow.

Open the generator, pick up a photo, hold it over the upload area. The dashed outline goes solid lemon yellow and the inside washes faintly warm. Search the generator's file for the word "yellow" as a colour value and you will not find it.

🧱
The metaphor for this module: a LEGO box with a paint chart taped inside the lid

The tray of loose bricks is src/components/ui/ — Button, Card, Input, about thirty of them. The finished models are src/components/blocks/ — the hero section, the pricing table, the generator panel. And taped inside the lid is one paint chart: change a swatch there and every brick in every model repaints at once, because no brick names a colour directly.

The one idea, before the details

Nothing in this interface names a colour, a corner radius or a shadow directly. Everything names a role — primary, card, border, muted-foreground — and the roles get their values in one file, twice: once for light mode, once for dark.

🚫
What the app never says

"Paint this button #F5D547." A hex colour typed straight onto an element is a dead end: it looks right today and wrong after the next theme tweak.

✅
What it says instead

"Paint this button with whatever primary currently means." One sentence in one file decides what that is, for the whole app, in both light and dark.

🌗
Which is why dark mode is free

The whole app can flip to dark mode without a single button, card or input knowing dark mode exists.

Four layers make that journey possible. Click through them — each tab is a real file in this project.

The paint chart — src/app/theme.css. Inside the :root block, raw colour values get given role names. A second block further down, .dark, redefines the same names with different values.

CODE 
  --primary: oklch(0.9 0.15 85);            /* Lemon Yellow */
  --primary-foreground: oklch(0.17 0 0);
  --secondary: oklch(0.8 0.08 200);         /* Sky Blue */
  --secondary-foreground: oklch(0.17 0 0);
  --muted: oklch(0.95 0.02 90);            /* Lighter gray */
  --muted-foreground: oklch(0.4 0.02 50);
  --accent: oklch(0.8 0.15 60);             /* Coral Orange */
  --accent-foreground: oklch(0.17 0 0);
  --destructive: oklch(0.7 0.2 25);           /* Tomato Red */
PLAIN ENGLISH

Each of these is a CSS variable — a named value. This one is not called "yellow", it is called "the main colour", and today the main colour happens to be lemon.

Every background role gets a matching foreground — the ink that goes on top. Near-black here, so text on yellow stays readable.

The app's second voice: sky blue, with its own matching ink. This is what the secondary buttons use.

The quiet pair: a pale background and a soft grey text colour, for captions, hints and placeholder text.

Coral orange for highlights and hover states — plus, again, the ink that belongs on it.

And the "are you sure?" red. Every delete button in the app reads this one name.

oklch is just a way of spelling a colour: how light, how vivid, which hue.

Nine role names, nine values. Swap the values, and every screen in the app is wearing a new outfit.

The bridge — further down the same file. This block is what turns a role name into something you can actually type on an element.

CODE 
@theme inline {
  --color-background: var(--background);
  --color-foreground: var(--foreground);
  --color-card: var(--card);
  --color-card-foreground: var(--card-foreground);
  --color-popover: var(--popover);
  --color-popover-foreground: var(--popover-foreground);
  --color-primary: var(--primary);
  --color-primary-foreground: var(--primary-foreground);
PLAIN ENGLISH

"Here is my palette, Tailwind — register every one of these as a colour you know about."

The page background and the main text colour get registered first.

Then the card surface and the ink that sits on cards.

Then popovers — the little floating panels that appear over the page.

var(--primary) means "go and read whatever --primary currently is". It does not copy the yellow, it points at it.

That pointing is the whole trick: registered once here, the value can still change underneath — which is exactly what the .dark block does.

The payoff of this one line: the class name bg-primary now exists and works.

Layer 1 decides what the colour is. Layer 2 decides that you can type it.

The utility classes — Tailwind. Honestly: it looks noisy. In exchange you never have to invent a name like .upload-box-inner-wrapper again.

Traditional CSS means writing the look in one file and the class names in another, then keeping the two in sync forever. Tailwind puts tiny single-purpose classes directly on the element instead.

bg-primary Background = the primary role. This is hop 4 of the yellow's journey.
text-muted-foreground Text = the quiet grey. Used on every hint and caption in the generator.
border-2 border-dashed A 2-pixel dashed outline — the resting state of the upload box.
rounded-xl Extra-large rounded corners, sized from the app's single --radius setting.
grid lg:grid-cols-2 One column normally; two side-by-side once the screen is wide. lg: is a responsive breakpoint.
hover:bg-primary/90 On hover, the same yellow at 90% strength. Prefixes stack conditions onto a class.

Every one of these is real, copied from the generator panel and the button file you are about to see.

The bricks — Shadcn UI. The crucial, easily-missed part: it is not a library you install and import from. Its components are copied into your own repository as ordinary files you own.

That is why src/components/ui/button.tsx is only 59 lines and sitting right there in the project. Here is a whole brick, in full.

CODE 
function Card({ className, ...props }: React.ComponentProps<"div">) {
  return (
    <div
      data-slot="card"
      className={cn(
        "bg-card text-card-foreground flex flex-col gap-6 rounded-xl border py-6 shadow-sm",
        className
      )}
      {...props}
    />
  )
}
PLAIN ENGLISH

Define a component called Card. It accepts a className (extra classes the caller wants to add) plus anything else passed to it.

Here is what it puts on the screen…

…a plain div. That is all a Card really is: a box.

Stamp it with a data- attribute that says "this is a card". Remember this line — it becomes a back door in a moment.

Now build the class list with cn(), the next screen's star.

Card's own opinions: card background, matching ink, children stacked with a gap, rounded corners, a border, vertical padding, small shadow.

…followed by whatever the caller passed in, which is allowed to override the opinions above.

Close the class list.

Pass everything else straight through — the click handler, the id, the contents, all of it.

Notice: not one colour, size or shadow value in that file. Only role names.

The six-line file that shows up everywhere

You just saw cn() inside Card. It is in essentially every component in this project. Here is the entire thing.

CODE 
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}
PLAIN ENGLISH

Borrow clsx — it glues class names together and drops any that are false.

Borrow twMerge — the referee that settles fights between conflicting classes.

(Blank line. The imports are done.)

Make a function called cn that accepts any number of class-name bits — strings, or conditions that may produce nothing.

Glue them all together, then hand the result to the referee and return the verdict.

Done. Six lines, used thousands of times.

Why the referee matters

If a component bakes in px-4 and you pass px-8, plain gluing would put both in the page and leave the browser to decide by an obscure rulebook.

✕
Without twMerge

"px-4 px-8" — both survive. Which one wins depends on specificity and stylesheet order. Fun to debug at 11pm.

✓
With twMerge

"px-8" — the referee notices the two are arguing about the same thing, deletes the earlier one, keeps the later one. Every time, predictably.

🎛️
This is the rule that makes bricks reusable

A component can hold strong opinions about how it looks and still let any caller override them, because the caller's classes always go last into cn(). Opinionated by default, overridable on request.

One button component, six different looks

The app does not have six button files. It has one, plus a lookup table that turns a word like outline into a string of classes.

The table lives in src/components/ui/button.tsx and is built with cva.

CODE 
    variants: {
      variant: {
        default:
          "bg-primary text-primary-foreground shadow-xs hover:bg-primary/90",
        destructive:
          "bg-destructive text-white shadow-xs hover:bg-destructive/90 focus-visible:ring-destructive/20 dark:focus-visible:ring-destructive/40 dark:bg-destructive/60",
        outline:
          "border bg-background shadow-xs hover:bg-accent hover:text-accent-foreground dark:bg-input/30 dark:border-input dark:hover:bg-input/50",
        secondary:
          "bg-secondary text-secondary-foreground shadow-xs hover:bg-secondary/80",
        ghost:
          "hover:bg-accent hover:text-accent-foreground dark:hover:bg-accent/50",
        link: "text-primary underline-offset-4 hover:underline",
      },
PLAIN ENGLISH

"Here are the ways this button is allowed to differ."

The first way is called variant — the word you type as variant="…" when you use the button.

default — the yellow one. Background = primary, ink = the matching foreground, tiny shadow, and on hover the same yellow at 90% strength. This is the Generate button.

destructive — the red one, with a red focus ring, and slightly different values when the page is in dark mode (that is what the dark: prefix means).

outline — a border and the page background, going coral on hover. Quiet until you touch it.

secondary — identical shape, sky blue instead of lemon. One token swapped.

ghost — nothing at all until hover. Used for icon buttons that should not shout.

link — not a box at all; it looks like a text link and underlines on hover.

End of the look menu. Six entries, one component, zero duplicate files.

💡
Aha! Indirection is a superpower you can ask for

"Use the secondary token, not a hex value" and "add a variant to the existing buttonVariants, don't write a new component" are two of the highest-value sentences you can say to an AI coding assistant. They are the difference between a change that lands in one place and a change that lands in forty.

Back to the glow

Now the opening hook decodes. This is the real upload box from imagen-client.tsx — one true-or-false value swapping one set of class names for another.

PLAIN ENGLISH

Work out this box's classes fresh, every time the screen redraws.

Always true: at least 400 pixels tall, extra-rounded corners, a 2-pixel dashed outline, animate any change over 300 milliseconds, show a pointer cursor.

Are there already photos in the box? Then just lay them out. If it is empty, centre the "drop a photo here" message instead.

dragActive is a boolean: is a file being dragged over the box right now?

Yes → solid yellow outline plus a 10%-strength yellow wash. That is the glow.

No → muted grey outline, turning yellow only when the mouse hovers, with an even fainter 5% wash.

Hand the finished class list to the box.

🔀
State goes in, classes come out

dragActive is flipped true by onDragOver and false by onDragLeave. Everything else follows automatically.

🚫
No animation library. No manual page editing.

Nothing here reaches into the page and repaints a pixel. The app describes what the box should look like; the browser does the rest.

The tray of bricks and the finished models

Two folders, two completely different jobs. Getting this distinction right is most of what "keeping a codebase tidy" means in practice.

components/ everything the user looks at
ui/ the loose bricks — generic, reusable, know nothing about this app
button.tsx59 lines, six variants
card.tsxa box with a border and a gap
input.tsxa text field, styled
blocks/ the finished models — built from bricks, and they know this app
imagen-wrapper/the whole generator panel
form/the feedback and settings forms
🧱

Bricks (ui/)

No business logic, no app text, no data. You could lift button.tsx into a completely different project tomorrow. Safe to reuse anywhere.

🏰

Models (blocks/)

These know about this app — its wording, its uploads, its Generate button. Reusing one somewhere else would drag the whole app along with it.

🗣️

How to say it

"Build this out of the existing ui/ components and put the new panel in blocks/" is a one-sentence architecture instruction an AI will follow happily.

The back door: restyling every brick without touching it

Remember data-slot="card" stamped on the Card component? Shadcn stamps one on every component it ships. This project uses those stamps as a back door.

CODE 
[data-slot="card"] {
  background: var(--card);
  border: 2px solid var(--border);
  border-radius: var(--radius);
  box-shadow: none;
}
PLAIN ENGLISH

"Find every element in the entire app carrying the card stamp."

Give it whatever --card currently means as its background.

Give it a chunky 2-pixel outline instead of the default hairline — this app wants a drawn-on-paper look.

Corner roundness comes from the one --radius knob, so it stays in step with everything else.

And kill the soft drop shadow entirely. Flat, not floaty.

Result: every card in the app restyled, and card.tsx was never opened.

🔨
A lovely trick with a sharp edge

This works because the rule and the stamp agree with each other. When they quietly stop agreeing, nothing errors — the styling just never happens. Module 5 has the version of this that fails in exactly that way.

The two switches in the header

Both toggles look like magic and are, in fact, one small change repeated at scale. Neither one asks any component to cooperate.

1
🌗 Dark mode — one class on the page root

ThemeProvider in src/contexts/theme-context.tsx adds the class dark to the outermost element of the page. The .dark block in theme.css then takes over every role name at once. One class, whole app repainted, and button.tsx never hears about it.

2
🌍 Language — one segment of the URL

LocaleSwitcher in src/components/ui/locale-switcher.tsx rewrites the language prefix in the web address (/zh/showcase). Next.js re-renders the page on the server in that language and sends it back. The language is not hidden in the app's memory — it is in the link, so it can be shared.

Two ways to build a form, both correct

The generator panel is hand-rolled: a plain text box, a plain state value per control, no validation tool. The app's other forms take the opposite route.

CODE 
function buildFieldSchema(field: FormFieldType) {
  let schema = z.string();

  if (field.validation?.required) {
    schema = schema.min(1, {
      message: field.validation.message || `${field.title} is required`,
    });
  }
PLAIN ENGLISH

Take one field's description and turn it into a schema — a rule-sheet the form can check itself against.

Start from the loosest possible rule: "this answer is some text". z is Zod, the rule-writing tool.

(Blank line, just for breathing room.)

Did whoever defined this field mark it as required? The ?. means "look, but do not crash if there are no validation settings at all".

Then tighten the rule: the answer must be at least 1 character long.

And if it is not, show this message — the custom one if someone wrote it, otherwise fall back to "Field name is required".

Done with this field. The red outline, the error text and the blocked submit button all follow from that one rule, automatically.

✋

Hand-rolled (the generator)

A prompt box, a style picker, an upload area. You hold each value yourself and check nothing. Perfectly fine for three controls you fully own.

📋

Declared (feedback, API keys)

React Hook Form plus Zod. State the rules out loud once; errors, outlines and blocked submits come free.

⚖️

The deciding factor

Not the size of the form — the complexity of its rules. The moment a rule is worth stating out loud, declaring it beats hand-checking it.

Four decisions

Not a memory test. Each one is a request you could plausibly get on a Tuesday — decide what you would ask an AI assistant to do.

A designer wants every card in the app to have corners twice as round. Where is the one-line change?

You need a button that looks like all the others but is green, for "Export". What is the best instruction to give an AI assistant?

A component has px-4 baked into its own class list. You pass it className="px-8". What actually renders — and why is it not a coin flip?

The generator's prompt box is a plain text area with a plain state value. The feedback form uses Zod. What actually decides which approach a new form should use?

What you can do with this now

🎨
Ask for tokens, never for hex

"Use the muted-foreground token" gets you a change that survives the next theme tweak and works in dark mode for free.

🧱
Ask for a variant, not a new component

Extending an existing brick keeps forty buttons in agreement. Cloning one is how an interface drifts into forty shades of almost-yellow.

📍
Say where new work should live

Generic and reusable goes in ui/. Knows-about-this-app goes in blocks/. One sentence, and the codebase stays navigable.
