The Journey of One Photo

You drop a photo onto the box and click Generate. For four seconds, nothing visible happens. Here is everything that happens in those four seconds.

What this thing actually does

Charlie & Lola AI is a website with one job. You drag in a photo of yourself, or your dog, or a toy, and a few seconds later you get the same subject redrawn in the scratchy, flat-colour style of the British children's cartoon Charlie and Lola.

Then you download it, or copy a link to share it. That is the entire product.

Same subject, redrawn. Download it or copy the share link.

Everything in this course is about the machinery behind that one button — and about the visual building blocks the interface is made from.

Stations 1–2: the photo never leaves the page (yet)

Here is the surprise. When you drop a photo on the box and the thumbnail appears instantly, nothing has been sent anywhere. Your film is still sitting on your side of the counter.

The browser reads the file off your disk and turns it into text that the page can display immediately. That is stations 1 and 2, and they are entirely local.

1
The file lands in the box

Drag-and-drop, or the file picker — either way the browser hands over a File

2
FileReader converts it to text

The picture becomes one enormous string of letters and numbers

3
The thumbnail appears

That string can be pasted straight into an image tag, so the preview is instant

This is the function that does it, from the real file. Read the code on the left; the plain English on the right walks the same path.

src/components/blocks/imagen-wrapper/imagen-client.tsx 
  const handleFileUpload = (file: File) => {
    if (uploadedImages.length >= 5) {
      toast.error(t.upload.max_images_error);
      return;
    }

    const reader = new FileReader();
    reader.onload = (e) => {
      const imageData = e.target?.result as string;
      setUploadedImages(prev => [...prev, imageData]);
      setGeneratedImage(null);
    };
    reader.readAsDataURL(file);
  };
Plain English

Whenever a file arrives, run these steps on it.

First, a bouncer check: if five pictures are already loaded, show a polite error and stop right here.

Otherwise, hire a FileReader — the browser's built-in tool for turning a file into something the page can use.

Reading takes a moment, so leave instructions for when it finishes: "when you're done, do this."

The finished result is a long text string. Grab it.

Add that string to the list of uploaded images, keeping the ones already there.

Clear any previous cartoon result, so the old output does not sit next to a new input.

And finally — the line that actually starts the work — read the file, as a data URL.

Two things in there are worth knowing by name.

📄

data URL

A data URL is the entire picture rewritten as text. It starts data:image/png;base64, and runs for thousands of characters.

🧠

state

setUploadedImages updates the component's state. Change state, and React repaints the screen for you.

✨
Aha: an image is just text if you squint

Base64 and data URLs mean the exact same picture can travel as a string of letters through channels that only carry text. That is why an AI service can hand a picture back to you over a plain text connection.

Station 3: packing the parcel

You click Generate. Now the film goes over the counter — and this is the moment the photo leaves your computer.

The page's code gathers the uploaded images and every setting into one parcel, then hands it to the app's own server.

Plain English

Get an empty parcel. FormData can hold text labels and real files side by side.

Label it: we are turning an image into another image, not writing one from scratch.

Hard-code the style to charlie-lola. This app only makes one look, so this is never a choice the visitor makes.

Attach the shape you picked (square, portrait) and the file type you want back.

Hard-code the quality tier too — another decision the app makes for you.

If you typed anything into the extra-instructions box, and it is not just blank spaces, include it.

Now for the pictures. Walk through the uploaded ones, one at a time.

Remember each one is currently a long text string. Read that string back...

...and turn it into a blob: the real bytes of the file, rather than the text version.

Drop it into the parcel under a numbered name: image_0, image_1, and so on.

Note down how many pictures are in there, so the server does not have to guess.

Then hand the parcel over the counter — to /api/generate-cyberpunk, the app's own endpoint.

POST means we are sending something, not just asking for something.

And the parcel itself is the body of the request.

Notice what is in the parcel: five text settings, then the images themselves. One container, two very different kinds of cargo.

mode image2image — start from a picture, do not invent one from words alone
style Always charlie-lola. Hard-coded, not a setting the visitor can change
aspectRatio The shape of the result — square, portrait, landscape
outputFormat Which kind of image file you get back
customPrompt Optional extra wording from you — only included if you actually typed something
image_0 … image_4 The pictures, as real file data
😅
Yes, it says "cyberpunk"

The route is called /api/generate-cyberpunk even though the app makes children's-book art. It is a leftover name from the template this app was built from. Module 5 takes stale naming seriously — for now, just enjoy it.

Stations 6–7: the picture comes back as text

Behind the wall, Gemini has drawn something. It cannot post you a photograph down a wire, so it sends the picture the only way a text connection allows: as base64.

The server gives it a name and, if all else fails, wraps it straight back up as a data URL.

src/app/api/generate-cyberpunk/route.ts 
    // Generate filename and store the image
    const batch = getUuid();
    const fileExtension = generatedImageMimeType.split('/')[1];
    const filename = `charlie-lola-${batch}.${fileExtension}`;

    let finalImageUrl = `data:${generatedImageMimeType};base64,${generatedImageData}`;
Plain English

A note-to-self in the code, for whoever reads it next.

Mint a unique ID so this result gets a filename nobody else will ever collide with.

Gemini told us the picture is, say, image/png. Chop that in half and keep the second bit: png. That is the MIME type becoming a file extension.

Glue them together: charlie-lola-3f2a9c1b.png.

And build a fallback address — the whole picture as a data URL — so there is always something to show, even before it reaches cloud storage.

Whatever address wins — the storage link or the data URL — it travels back to the browser wrapped in JSON. And then station 7 is four lines long.

Plain English

Unwrap the response from the server and read what is inside.

Two conditions, both of which must hold: the app's own status code says all-clear (zero means fine here), AND there is genuinely an image address in the reply.

Only then, put that address into state — and React repaints the right-hand panel with your cartoon.

Worth pausing on: the server can reply perfectly well and still be reporting a failure inside the message. "The request succeeded" and "the image appeared" are two separate claims.

02

Front of House, Backstage

Every file in this app runs on one of two machines. Here's the wall between them — and how to tell, at a glance, which side any file is on.

The key that pays for everything

The API key that pays Google for every image this app generates is sitting in a file right now. If it ever reached a visitor's browser, a stranger could run up the bill on somebody else's card.

Module 1 followed one photo from the upload box to the moment it crossed from the browser to the server. This module is about that crossing itself: what it is, why it exists, and how to tell which side of it you're standing on.

⚠️
This is the #1 thing AI coding assistants get wrong

Ask an AI for a feature in a Next.js app and it will happily put browser-only code in a server file, or read a secret in a browser file. The errors that come back are famously baffling — "useState is not a function", "hydration mismatch". Spotting the side a file belongs to lets you correct it in one sentence instead of ten rounds of guessing.

A theatre has two halves

Front of house is what the audience sees: the stage, the actors, the programme in their hands. Backstage is the fly system, the lighting desk, and the safe in the manager's office with the keys in it.

The audience can walk right up to the edge of the stage. They can never walk into that office. That single fact is the whole architecture of this app.

🎭
Front of house = the visitor's browser

Buttons, drag-and-drop, spinners, previews. Everything here was shipped to a stranger's laptop, and a stranger can read every line of it.

🔐
Backstage = the company's server

Translation files, database lookups, the API keys. Nothing here is ever sent out — only the results of what happens here.

🚪
The stage door = one line of text

A file that starts with 'use client' is front of house. A file without it stays backstage. That's it — that's the whole mechanism.

🎬
Why not let ImagenClient fetch its own text?

Because doing it backstage means the correct words are already in the page before any JavaScript runs — the visitor sees real text instantly, and search engines see real text too. Fetching it front of house would mean a flash of emptiness first.

✍️
Naming is the entire security mechanism

There's no vault and no permission list — the framework decides purely by reading the name. Which means adding six characters to the front of a key's name is a real, published leak.

Three ways to tell which side you're on

1️⃣

Read the top line

'use client' on line 1 means front of house. No line 1 means backstage — that's the default in this app.

2️⃣

Look at what it touches

Clicks, typing, remembering, spinners → must be front of house. Waiting on a lookup, reading secrets → must be backstage.

3️⃣

Ask who's allowed to see it

If a stranger reading this file would be a problem, it cannot be front of house. No exceptions, no clever workarounds.

The brief you are allowed to rewrite

This is the actual prompt the app sends, sitting in the source as one very long line. Read it as what it is: instructions to a freelancer.

📜
From the brief itself

"…thin sketchy outlines, flat colors, childlike proportions, playful hand-drawn charm…"

"Retain the subject's original clothing, hairstyle, facial features, accessories, skin tone, pose, and expression…"

"Negative Prompt: No realistic shading, no detailed rendering, no anime or manga style, no 3D modeling, no photographic textures!"

Every good image brief has the same three-part shape. This structure transfers to any image model you will ever use.

🎯

What to make

The look you want, in concrete visual words: sketchy outlines, flat colours, childlike proportions.

🔒

What to preserve

The things from the photo that must survive: clothing, hairstyle, skin tone, pose, expression.

🚫

What to forbid

The negative prompt — the list of default habits the model must resist.

Notice what this means for you: if the output keeps losing people's glasses, the fix is a few words added to the "retain" list. No new logic, no new deploy of clever code — just better writing.

Opening the envelope

Gemini does not reply with a picture. It replies with candidates: a bag of parts, some text, hopefully one image. The route rummages until it finds the picture.

PLAIN ENGLISH

Take the first answer Gemini sent, and go through its parts one at a time.

Is this part a file rather than words? (Text parts have no inlineData.)

Yes — so keep the picture data.

And keep the note saying what kind of image file it is.

Close the "if it is a file" check.

Close the loop. If we got all the way here without finding one, there is no image — and the app says so.

🧭
Worth remembering when you debug

If a user ever sees "No image data found in Gemini API response", this loop ran and found nothing. The call worked, the key worked — the artist just replied with words instead of a drawing, usually a polite refusal.

Six keys, taking turns

Google puts a daily ceiling on each account. So this app holds six keys and rotates through them — a pattern called round-robin, the same way a deck of chores rotates through a house of flatmates.

💡
Aha: a rate limit is a nightclub capacity, not a fine

A rate limit does not charge you more when you go over. It stops letting you in. That is why apps pool keys: six doors instead of one, same club.

⚠️
The pool lives in memory, not in a database

The counters are in-memory, held by a single copy of the pool object (a singleton). Run three server copies and each has its own private pool with its own idea of which keys are burnt out. Restart, and the app forgets everything.

Those six keys are environment variables, set on the server and never shipped to your browser.

GEMINI_API_KEY The first key. If only this one is set, the pool is a pool of one
GEMINI_API_KEY_2 … _5 The extra doors — optional, and each one multiplies daily capacity
STORAGE_ENDPOINT Where finished pictures get uploaded — the address of the file warehouse
STORAGE_ACCESS_KEY The username half of the warehouse credentials
STORAGE_SECRET_KEY The password half. Server-side only, always
STORAGE_BUCKET Which shelf inside the warehouse these images belong on

CODE 
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}
PLAIN ENGLISH

Borrow clsx — it glues class names together and drops any that are false.

Borrow twMerge — the referee that settles fights between conflicting classes.

(Blank line. The imports are done.)

Make a function called cn that accepts any number of class-name bits — strings, or conditions that may produce nothing.

Glue them all together, then hand the result to the referee and return the verdict.

Done. Six lines, used thousands of times.

Why the referee matters

If a component bakes in px-4 and you pass px-8, plain gluing would put both in the page and leave the browser to decide by an obscure rulebook.

✕
Without twMerge

"px-4 px-8" — both survive. Which one wins depends on specificity and stylesheet order. Fun to debug at 11pm.

✓
With twMerge

"px-8" — the referee notices the two are arguing about the same thing, deletes the earlier one, keeps the later one. Every time, predictably.

🎛️
This is the rule that makes bricks reusable

A component can hold strong opinions about how it looks and still let any caller override them, because the caller's classes always go last into cn(). Opinionated by default, overridable on request.

export function respJson(code: number, message: string, data?: any) {
  let json: { code: number; message: string; data?: any } = {

    message: message,
  };
  if (data) {
    json.data = data;

What the five have in common

💡
Aha: silence is a symptom

A branch that never runs, a rule that matches nothing and a setter that is never called all produce exactly zero errors. Working code and disconnected code look identical from the outside — which is why "it does not crash" is not evidence that it works.

An inspector does not need to know how a house was built to tap the walls. Here is the clipboard — five questions you can ask about your own project this afternoon.

🔌

Is this setter ever called?

"Search the file for every place setAspectRatio is used." If the only hit is where it was created, the control is decorative.

🔤

Do both sides spell it the same?

"List the exact field names the server sends and the ones the client reads." Data crossing a network is never spell-checked by anybody.

🎯

Does this selector match anything?

"Show me an element that has both of these attributes." A style rule for a thing that does not exist is silent, tidy and useless.

🏷️

Does the label match the behaviour?

Read the button out loud, then read what it actually does. Words go stale faster than logic, and nothing checks them.

🔗

Is it wired all the way through?

Anything hand-copied from place to place has as many failure points as it has hops. Count the hops before you add the sixth one.

🤖
For steering AI: the three sentences that end a bug loop

"Why is this broken?" gets you guesses, and the next twenty minutes get you more guesses. Say these three things instead, in this order.

1
Name the station

"This is the client-side handling of the response, in imagen-client.tsx." You learned the seven stations in module 1 for exactly this sentence.

2
Name the mismatch

"The server sends a field called message. The client reads result.msg." A fact, not a symptom. Nothing left to diagnose.

3
Name the fix you want

"Change the client to read result.message. Do not touch resp.ts — everything else in the app depends on it." Otherwise a helpful assistant may fix it from the wrong end and cause a regression in ten other places.

Guesses in, guesses out. Specifics in, patches out.
