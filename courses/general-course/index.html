The Envelope You Never See Behind

Picture a one-hour photo lab. You slide your film into a paper envelope, write "matte finish, 4x6" on the outside, and post it through a slot in the wall. You never see what happens back there.

Your browser and the server are two separate computers that can only pass each other messages — nothing more. Everything an app does is really just: package a message, send it, wait, unpack the reply.

In this app: the envelope is your request; the slot is the API endpoint; the back room is the server; and the prints coming back are the response.

Meet the Cast — How the Code Is Organised

Every file has a job. Once you know the roles, you know exactly where to tell an AI to make a change.

A Codebase Is a Film Production

In Module 1, a message travelled through five different pieces of code — and nobody introduced them. Time to meet the cast, because the single most useful thing you can tell an AI coding assistant is where a change belongs.

🎭

The Cast

The parts you actually see — buttons, upload boxes, preview panels. In code, these are React components living in src/components/blocks/.

🎬

The Crew

They work behind the camera and never appear in the shot: API routes, services, models, and the database. This is where the actual business logic lives.

🪑

Props Department

A shelf of generic, reusable objects any scene can borrow — a chair, a mug, a lamp. In code: 37 small pieces like buttons, cards, and dialogs in src/components/ui/.

🪜

Chain of Command

An actor doesn't wander into the accounts office to rewrite the budget. Requests travel up a strict chain, one step at a time — nobody skips ahead.

When you tell an AI "add a rule that Pro users get 3 free generations a day," it has to put that rule somewhere. Knowing which department owns that rule is often the difference between a codebase that survives a year of changes and one that quietly falls apart before you even deploy it again.

The Map: Who Lives Where

Here's the real top-level folder structure of src/ — annotated with each department's film-crew role.

app/ The stage. Every page and every route — an endpoint — lives here. The folder path IS the address.
components/blocks/ The cast. Big page sections: hero, pricing, faq, footer, imagen-wrapper.
components/ui/ Props department. 37 small generic pieces: button.tsx, card.tsx, dialog.tsx, tabs.tsx.
services/ The crew chiefs. Business rules: credit.ts, order.ts, user.ts, stripe.ts, affiliate.ts.
models/ The records office. The only files allowed to touch the database: user.ts, credit.ts, order.ts, post.ts.
db/ The filing cabinet itself.
schema.ts The schema — table shapes.
index.ts The live connection to the database.
auth/ Security. Who you are — covered in Module 3.
i18n/ Translation department. English and Chinese text — Module 6.
lib/ The toolbox. Small helpers used by everyone: hash.ts, time.ts, resp.ts, storage.ts.
aisdk/ The specialist rig. A hand-built adapter for the Kling video-generation service.

Folders Become Web Addresses

In Next.js — the framework this app runs on — folders under src/app/ literally become the URL path in your browser bar.

[locale]/(default)/pricing/page.tsx becomes charlieandlola.net/en/pricing
api/checkout/route.ts becomes charlieandlola.net/api/checkout
(admin)/admin/orders/page.tsx becomes charlieandlola.net/admin/orders

Two notations make this readable once you know the trick:

[ ]
[locale] — square brackets

Means "anything goes here, and tell me what it was." That's how /en/pricing and /zh/pricing are the same one file.

( )
(default), (admin), (console) — round brackets

Mean "this folder is for organizing only." It does not appear in the URL at all — genuinely confusing the first time you see it.

Who Are You? Sign-In, Sessions, and Trust

How a click on "Sign in with Google" turns into a stamped, tamper-evident wristband your Browser carries everywhere.

Two Very Different Jobs

You can use this app without signing in — you just can't download. Last module we spotted the image route quietly calling getUserUuid() and promised we'd open that box. This is that box.

🎟️

The Gate

Once, you queue up and prove who you are the hard way — passport, booking reference, a good look at your face.

🎫

The Wristband

After that, nobody checks your passport again. Every bar, every stage, every backstage door just glances at the wristband.

⏳

Tamper-Evident, and It Expires

You can't peel it off and hand it to a friend without it showing. And it stops working at the end of the weekend.

The gate is the sign-in flow. The wristband is a session — a signed cookie holding a signed token. "Show me your wristband" is getUserUuid().

💡
Key Insight

Authenticating you is expensive and happens once. Remembering who you are is cheap and happens on every single request. That's different from authorisation, which comes after. Confusing these jobs is where most auth bugs come from — and this app never stores your Google password. It never even sees it.

The app offers several ways to prove who you are. Every one of them is a different door — but they all lead into the same room.

There Is No Balance

Last module ended on a cliffhanger: new accounts get 30 credits, an image costs 10, so what happens on the fourth one? The honest answer is that you run out — and the app has to know that with total certainty.

Picture the paper stub in the back of an old chequebook. One line per transaction: date, description, +£200 or −£35. The rule that makes it trustworthy is this: you never rub out the balance and write a new one. You only ever add a line.

The Day the Database Vanished

While making this course, we tried to connect to this app's database. It answered:

💀
tenant or user not found

The Supabase project had been deleted — most likely reclaimed as an idle free-tier project. Nothing in the code is wrong. The code is fine. The thing the code depends on stopped existing.

Learn the shape of that error, because you will meet it again. It appeared at the connection stage — before a single one of the app's queries ever ran. That timing is the tell.

1
Errors at the connection stage

"Not found", "authentication failed", "could not connect" — before any of your queries run. Almost never your code. Suspect the address, the credentials, or the service itself.

2
Errors from a specific query

"column does not exist", "duplicate key". The connection is fine — this is your code, or a migration that was never run.

3
No error, wrong answer

Everything "works" but the numbers are wrong. The hardest kind. Module 7 is about these.

Two things would have caught this earlier: a health check that actually touches the database rather than just returning "OK", and knowing in advance that free tiers reclaim idle projects.

When the database does exist, the app does not open a new connection for every question it asks. Opening one is slow, so it keeps a small set open and reuses them — a connection pool.

max: 10 At most ten open lines at once. The eleventh request waits its turn rather than overwhelming the database.
idle_timeout: 30 A line sitting unused for 30 seconds gets hung up. Do not pay to hold lines nobody is talking on.
connect_timeout: 10 If dialling takes more than 10 seconds, give up and fail loudly instead of hanging forever.

When It Breaks

Six modules of how it works. Here is the part nobody writes down: what to do at 11pm when a user emails "it's broken" and you have no idea where to start.

Nobody Guesses in Aviation

When an aircraft has a bad day, investigators do not sit in a room theorising. They pull the flight recorder and read what the aircraft was actually doing, second by second, until reality stops matching what everyone assumed.

💡
You Do Not Debug by Thinking Harder

You debug by getting more instrument readings. Every hour lost to a bug is usually an hour spent theorising instead of looking. Debugging is closer to reading a black box recorder than to having a brilliant idea.

Here is the shape of the whole thing. You already know the route a request takes: Browser → Server → outside service → Database → back. A bug is simply the first point on that route where reality stopped matching expectation.

Every observation you make cuts the remaining search space roughly in half. Engineers call that a binary search, and it turns an unbounded mystery into about five questions.

🗣️
Why This Is the Most Valuable Module for You

AI assistants are excellent at fixing a problem you can describe precisely, and terrible at finding one you can only describe as "it doesn't work". Vague reports send them into loops of speculative rewrites, each one leaving the codebase slightly worse. One precise sentence — "the POST to /api/generate-cyberpunk returns 200 with code -1 and message 'Insufficient credits', even though the balance shows 40" — usually gets fixed on the first try. This module is about how to write that sentence.

The Five-Question Ladder

For any bug, in any app, ask these in this order. The order matters — each question is cheap and rules out everything below it.

1
Did the request even leave the Browser?

Open dev tools and look at the Network tab. No request at all means the bug is in the click handler, not on the server. You have just eliminated the entire backend.

2
Did the Server receive it, and what did it answer?

Read the status code and the reply body. This app always answers with the same shape — { code, message, data }, where code: 0 means fine and code: -1 means an error with a human-readable message sitting right there.

3
Did an outside service refuse?

Gemini quota, Stripe signature, storage credentials. Critically: these appear in the server logs, never in the browser. If you have not looked at your logs, you have not looked.

4
Is the data actually what you think it is?

Go and look. Is there a credits row for that order number? Is the order status still created? Assumptions about data are where confident people lose whole evenings.

5
Is it the environment, not the code?

Works locally, fails in production? Suspect environment variables first, every single time. Module 3's missing GitHub sign-in button was exactly this.

Getting It Onto the Internet

First, the thing that surprises everyone: the code you write is not the code that runs. A build step turns TypeScript into JavaScript, pre-renders pages, and bundles everything into one folder that contains exactly what is needed to run and nothing else.

This app can be shipped three different ways, and each trade-off is worth knowing.

▲

Vercel

The default. Push to git and it builds and deploys itself. Easiest by a mile — and you are on their terms, including that 60-second ceiling.

☁️

Cloudflare Workers

Lives on its own branch, runs at the edge. Cheap and fast, more constraints — src/db/index.ts literally has an if (isCloudflareWorker) branch that opens exactly one database connection instead of a pool of ten.

🐳

Docker

A recipe that builds a self-contained box — a container — that runs identically anywhere. Most portable, most work.

The Docker recipe is worth one look, because two lines of it are pure professional habit.

CODE 

FROM base AS runner
WORKDIR /app
 
RUN addgroup --system --gid 1001 nodejs && \
    adduser --system --uid 1001 nextjs && \
    mkdir .next && \
    chown nextjs:nodejs .next
 
COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
 
USER nextjs
PLAIN ENGLISH

Start a fresh, clean box for actually running the app. The messy box that did the building is thrown away — this is a multi-stage build.

Work in a folder called /app.

Create a plain, unprivileged user called nextjs to run everything, and give it ownership of the folder it needs.

Copy in only the finished output from the build box — not the source code, not the build tools, not the notes.

Then switch to that limited user. If someone ever finds a way in, they arrive as nextjs, not as root — so a break-in cannot take the whole machine. Two lines, an enormous difference.

The Vocabulary You Now Own

This was the real payoff all along. These are not trivia — they are the words that let you tell an AI assistant precisely what you want, instead of describing it and hoping.

request / response One question, one answer. Everything on the web is this.
endpoint One specific address that answers one specific kind of question
session / token The signed wristband that says who you are, checked on every request
webhook Another service calling you, unprompted, when something really happened
