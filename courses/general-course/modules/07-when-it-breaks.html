When It Breaks

Six modules of how it works. Here is the part nobody writes down: what to do at 11pm when a user emails "it's broken" and you have no idea where to start.

Nobody Guesses in Aviation

When an aircraft has a bad day, investigators do not sit in a room theorising. They pull the flight recorder and read what the aircraft was actually doing, second by second, until reality stops matching what everyone assumed.

💡
You Do Not Debug by Thinking Harder

You debug by getting more instrument readings. Every hour lost to a bug is usually an hour spent theorising instead of looking. Debugging is closer to reading a black box recorder than to having a brilliant idea.

Here is the shape of the whole thing. You already know the route a request takes: Browser → Server → outside service → Database → back. A bug is simply the first point on that route where reality stopped matching expectation.

Every observation you make cuts the remaining search space roughly in half. Engineers call that a binary search, and it turns an unbounded mystery into about five questions.

🗣️
Why This Is the Most Valuable Module for You

AI assistants are excellent at fixing a problem you can describe precisely, and terrible at finding one you can only describe as "it doesn't work". Vague reports send them into loops of speculative rewrites, each one leaving the codebase slightly worse. One precise sentence — "the POST to /api/generate-cyberpunk returns 200 with code -1 and message 'Insufficient credits', even though the balance shows 40" — usually gets fixed on the first try. This module is about how to write that sentence.

The Five-Question Ladder

For any bug, in any app, ask these in this order. The order matters — each question is cheap and rules out everything below it.

1
Did the request even leave the Browser?

Open dev tools and look at the Network tab. No request at all means the bug is in the click handler, not on the server. You have just eliminated the entire backend.

2
Did the Server receive it, and what did it answer?

Read the status code and the reply body. This app always answers with the same shape — { code, message, data }, where code: 0 means fine and code: -1 means an error with a human-readable message sitting right there.

3
Did an outside service refuse?

Gemini quota, Stripe signature, storage credentials. Critically: these appear in the server logs, never in the browser. If you have not looked at your logs, you have not looked.

4
Is the data actually what you think it is?

Go and look. Is there a credits row for that order number? Is the order status still created? Assumptions about data are where confident people lose whole evenings.

5
Is it the environment, not the code?

Works locally, fails in production? Suspect environment variables first, every single time. Module 3's missing GitHub sign-in button was exactly this.

WHAT THE USER EXPERIENCES

Never show a negative balance. Fair enough.

Anyone with credits left counts as a paying user.

Hand back the real, correct balance. This is the normal, everything-is-fine path.

And here is the other exit. catch means "if anything at all went wrong above, come here instead". A database outage lands here.

Write a note in the log, where no customer will ever see it and, realistically, nor will you.

Then hand back the object created at the very top of the function — the one still full of zeros. The customer is told they have 0 credits. Not "we could not check". Zero. Confidently.

🤫
Say What Should Happen on Failure

When you ask an AI to "add error handling", this is very often what you get: a try/catch that swallows the problem and returns a plausible-looking default. Be specific instead: "if this fails, surface the error to the caller — do not return a default that looks like real data." A crash is honest. A confident wrong answer is not.

The Environment Gap

Works on the laptop, not in production. In this app, whole sign-in providers, the entire storage upload and the choice of payment company are all switched on and off by environment variables. Nearly always configuration, nearly never code.

Writing Your Own Flight Recorder

Before every AI call, this app writes down a block of context. Somebody sat and decided what they would want to know at 3am, and it shows.

CODE 

    console.log("=== Charlie and Lola API Request Details ===");
    console.log("Mode:", mode);
    console.log("Model:", model);
    console.log("Aspect Ratio:", aspectRatio);
    console.log("Output Format:", outputFormat);
    console.log("Style:", style);
    console.log("Custom Prompt:", customPrompt ? "Yes" : "No");
    console.log("Images uploaded:", images.length);
    console.log("User Registered:", isRegisteredUser);
    console.log("User UUID:", userUuid || "Guest user");
    console.log("===========================================");
PLAIN ENGLISH

Draw a line in the log so this block is findable by eye among thousands of others.

Record every setting that shaped this request: which mode, which AI model, what shape, what file format, which style.

Note whether the user typed their own instructions — but not what they typed. A deliberate choice: yes or no is enough to reproduce the problem.

How many images came in, whether the person was signed in, and who they were — or the word "Guest".

Close the block. Everything needed to recreate this exact request, and nothing that would be embarrassing to leak.

📝
Log the Inputs You Would Need to Reproduce It. Never Log Secrets.

Logs get copied into chat messages, support tickets and screenshots. API keys, passwords, tokens and full card details must never appear in them. "Custom prompt: Yes" is a perfect example of the discipline — enough to debug, not enough to expose anyone.

And then there are the limits you did not choose and cannot see. This is the entire vercel.json file:

CODE 

{
  "functions": {
    "app/api/**/*": {
      "maxDuration": 60,
      "memory": 1024
    }
  }
}
PLAIN ENGLISH

Settings for the bits of code that answer requests.

Apply these to every API address in the app — the stars mean "anything nested under here".

Hard ceiling: 60 seconds. Take longer and the request is killed mid-flight, whatever it was doing.

And about a gigabyte of working memory. Image generation takes around ten seconds, so there is headroom — but a slow day at Google, or a bigger image, eats into it invisibly.

Name the class of problem: limits you did not choose and cannot see. They are exactly why something works perfectly in testing and fails under load.

Getting It Onto the Internet

First, the thing that surprises everyone: the code you write is not the code that runs. A build step turns TypeScript into JavaScript, pre-renders pages, and bundles everything into one folder that contains exactly what is needed to run and nothing else.

This app can be shipped three different ways, and each trade-off is worth knowing.

▲

Vercel

The default. Push to git and it builds and deploys itself. Easiest by a mile — and you are on their terms, including that 60-second ceiling.

☁️

Cloudflare Workers

Lives on its own branch, runs at the edge. Cheap and fast, more constraints — src/db/index.ts literally has an if (isCloudflareWorker) branch that opens exactly one database connection instead of a pool of ten.

🐳

Docker

A recipe that builds a self-contained box — a container — that runs identically anywhere. Most portable, most work.

The Docker recipe is worth one look, because two lines of it are pure professional habit.

CODE 

FROM base AS runner
WORKDIR /app
 
RUN addgroup --system --gid 1001 nodejs && \
    adduser --system --uid 1001 nextjs && \
    mkdir .next && \
    chown nextjs:nodejs .next
 
COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
 
USER nextjs
PLAIN ENGLISH

Start a fresh, clean box for actually running the app. The messy box that did the building is thrown away — this is a multi-stage build.

Work in a folder called /app.

Create a plain, unprivileged user called nextjs to run everything, and give it ownership of the folder it needs.

Copy in only the finished output from the build box — not the source code, not the build tools, not the notes.

Then switch to that limited user. If someone ever finds a way in, they arrive as nextjs, not as root — so a break-in cannot take the whole machine. Two lines, an enormous difference.

The Pre-Flight Checklist

Read it aloud before every launch, on any project. "I'm sure it's fine" is not a check.

🔑
Environment variables set in production?

Not on your laptop — in production. All of them, including the ones you added last week.

🗄️
Database reachable from production?

Reachable from your laptop is not the same test. Firewall rules and connection limits differ.

📩
Webhook registered and pointing at the live domain?

The single most common launch-day payment bug, and you just watched it happen.

🔐
No secrets in the code?

Search the repo for anything that looks like a password or a key before you make it public.

📈
External quotas high enough for launch day?

Free-tier AI limits do not survive a good day on social media.

🔦
Can you see the logs?

Find out where they are before you need them, not at 11pm with users waiting.

The Vocabulary You Now Own

This was the real payoff all along. These are not trivia — they are the words that let you tell an AI assistant precisely what you want, instead of describing it and hoping.

request / response One question, one answer. Everything on the web is this.
endpoint One specific address that answers one specific kind of question
session / token The signed wristband that says who you are, checked on every request
webhook Another service calling you, unprompted, when something really happened
idempotent Safe to run twice. Say this word when asking for payment code.
append-only ledger Never overwrite a balance — add a line and sum them
schema / migration The blueprint, and the numbered reviewable permit that changes it
connection pool A few open lines held ready and shared, not a new call every time
rate limit / quota The cap on how much of someone else's service you may use
environment variable Settings outside the code. The first suspect in every works-here-not-there bug.
graceful degradation When part of it fails, the rest keeps working in a reduced way
locale / i18n Which language and region a visitor gets, and the machinery that serves it
component / variant A reusable interface piece, and its named looks
middleware A checkpoint every request passes through before reaching a page
server vs client Runs privately on their computer vs runs visibly on yours. Trust accordingly.

You Just Read a Real Production Codebase, End to End

Not a tutorial project — a live app with real customers, real money moving through it, a hardcoded password, a deleted database, and an endpoint named after a product that no longer exists. That is what all of them look like, including the ones built by teams of twenty.

You do not need to write any of this from scratch. You need to read it, recognise the shapes, and know the words — and you now do. The next time an AI assistant hands you something that smells off, you will be able to say exactly why.

Go and build something. And when it breaks, you already know which question to ask first.
