Following the Money

Thirty free credits, ten per image — so the fourth image is where this app has to become a business. The way it handles money is quietly the most carefully-built part of the whole codebase.

There Is No Balance

Last module ended on a cliffhanger: new accounts get 30 credits, an image costs 10, so what happens on the fourth one? The honest answer is that you run out — and the app has to know that with total certainty.

Picture the paper stub in the back of an old chequebook. One line per transaction: date, description, +£200 or −£35. The rule that makes it trustworthy is this: you never rub out the balance and write a new one. You only ever add a line.

+30 new_user — signed up on 3 March. Expires in one year.
−10 image_generation — first cartoon
−10 image_generation — second cartoon
+1000 order_pay — bought the Premium plan, order #7429
−10 image_generation — third cartoon

That list is a real table in this app's database, called credits. Look at the columns it does not have: there is no column called balance anywhere. Your balance is not a number the app keeps — it is the sum of those rows, added up fresh every time anyone asks.

💡
Never Overwrite a Balance. Always Append a Line.

Engineers call this an append-only ledger, and it is one of the most valuable instructions you can give an AI assistant. Ask for "add credits" and you will almost certainly get UPDATE users SET credits = credits - 10 — a single number being overwritten. That works right up until two requests land at the same moment, or a customer asks where their credits went, and then there is nothing to look at.

Buying: The Price Does Not Come From You

When you click a plan on the pricing page, your Browser sends the Server a small package of information — a POST request carrying three things: which product, which currency, which language.

🏷️

product_id

Which plan you clicked. Just a name, like premium.

💱

currency

Dollars or yuan — which price list to read from.

🌍

locale

Which language you are browsing in.

🚫

the price

Not sent. Not now, not ever. The Server looks it up itself.

CODE 

    // validate checkout params
    const page = await getPricingPage(locale);
    if (!page || !page.pricing || !page.pricing.items) {
      return respErr("invalid pricing table");
    }
 
    const item = page.pricing.items.find(
      (item: PricingItem) => item.product_id === product_id

    if (!item || !item.amount || !item.interval || !item.currency) {
      return respErr("invalid checkout params");
    }
PLAIN ENGLISH

A note for future readers: we are about to check that this order makes sense.

Load the Server's own price list for this language. Not the Browser's copy — the real one.

If the price list is missing or empty, stop immediately and say so. Never guess.

Search that list for the plan the visitor clicked, matching on its name.

If there is no such plan, or it has no price, no billing period or no currency, refuse the whole request.

Everything after this point uses item.amount — a number that came from the Server's own files, and never from you.

⚠️
Never Trust the Client With Anything That Matters

If the price arrived in the request, anyone could open dev tools, change amount to 1, and buy the $99 plan for one cent. The rule generalises far beyond money: the Browser is a place your code runs, not a source of truth. Anything the Server decides must be looked up by the Server.

The Plot Twist: Nobody Tells the Server You Paid

The Server creates an order row with status created, asks Stripe for a payment page, and sends your Browser there. Your card details never touch this app's servers.

Then you pay, and Stripe redirects you back. Here is the part that surprises everyone: that redirect is not proof of payment. Anyone could type that return address into their browser bar.

So Stripe does something separate. Its own servers make a request to your server, at a special address, saying "this actually happened". That call-back-when-it-is-real message is a webhook.

📦
The Delivery Firm Phones You Back

You do not stand at the door guessing whether the parcel arrived. The courier rings you when it is actually delivered. The customer walking back through your door is a hopeful sign; the courier's phone call is the fact.

Watch the whole conversation happen. Three participants, and one of them speaks up without being asked.

Two things in that conversation are worth pulling apart. First, how the Server knows the message really came from Stripe. Second, that last exchange — Stripe said the same thing twice.

Proving Who Sent It

The webhook address is a public address on the internet. Anyone can send a message to it claiming a payment succeeded — so every message arrives with a cryptographic signature attached, and the Server refuses to believe anything it cannot verify.

CODE 

    const sign = req.headers.get("stripe-signature") as string;
    const body = await req.text();
    if (!sign || !body) {
      throw new Error("invalid notify data");
    }
 
    const event = await stripe.webhooks.constructEventAsync(
      body,
      sign,
      stripeWebhookSecret
    );
 
    console.log("stripe notify event: ", event);
 
    switch (event.type) {
      case "checkout.session.completed": {
        // get checkout session
        const session = event.data.object;
        await handleCheckoutSession(stripe, session);
        break;
      }
PLAIN ENGLISH

Pull the signature Stripe attached to this message, and the raw text of the message itself.

If either one is missing, stop right here — this is not a message worth reading.

Hand all three to Stripe's own checking function: the message, the signature, and a shared secret only Stripe and this Server know.

If the fingerprint does not match, this line fails and nothing below it ever runs. A forged message dies here.

Write the verified message into the log, so there is a record if anyone needs to reconstruct what happened.

Stripe sends many kinds of message. Look at which kind this is and pick the matching branch.

If it is "the customer finished checking out", pull out the details and go do the actual work of marking the order paid.

Notice where stripeWebhookSecret comes from: an environment variable set on the server, never written into the code. If that secret is wrong, every real payment message gets rejected — and that is a very common launch-day bug.

Safe to Do Twice

Stripe will sometimes send the same webhook more than once. That is deliberate: if a network blip means the first message was not acknowledged, sending it again is far better than losing a payment.

Which puts the burden on your side. The code has to be safe to run twice — a property with a name worth learning: idempotent. Say that word to an AI assistant and the payment code you get back is immediately better.

CODE 

    // order already paied
    if (order.status === OrderStatus.Paid) {
      return;
    }
 
    // only update order status from created to paid
    if (order.status !== OrderStatus.Created) {
      throw new Error("invalid order status");
    }
 
    const paid_at = getIsoTimestr();
    await updateOrderStatus(
      order_no,
      OrderStatus.Paid,
      paid_at,
      paid_email,
      paid_detail
    );
 
    if (order.user_uuid) {
      if (order.credits > 0) {
        // increase credits for paied order
        await updateCreditForOrder(order as unknown as Order);
      }
PLAIN ENGLISH

A note from whoever wrote this — with a typo in it, because real codebases have typos.

Guard one: if this order is already marked paid, quietly stop. No error, no fuss, no second helping of credits.

If the order is in some other unexpected state — cancelled, say — that is a genuine problem, so raise a loud error instead of continuing.

Record the exact moment of payment.

Flip the order from created to paid, storing who paid and Stripe's full record of it alongside.

Only if this order belongs to a signed-in account, and only if it actually bought credits…

…add the credits. Which has a guard of its own.

That second guard lives in the credit service, and it is even simpler: before writing the +1000 line, look for a line that already carries this order number.

order.status === Paid Guard one — the order itself remembers it was already settled
findCreditByOrderNo Guard two — the ledger already has a line tagged with this order number, so stop

Two independent guards for the same mistake. That is not paranoia; that is what code touching money should look like.

Spending Is Just a Minus Sign

Generating an image spends 10 credits. Here is the entire mechanism for that — and the whole idea of the module is hiding on one line.

CODE 

    const new_credit: typeof creditsTable.$inferInsert = {
      trans_no: getSnowId(),
      created_at: new Date(getIsoTimestr()),
      expired_at: new Date(expired_at),
      user_uuid: user_uuid,
      trans_type: trans_type,
      credits: 0 - credits,
      order_no: order_no,
    };
    await insertCredit(new_credit);
PLAIN ENGLISH

Build one new ledger line, ready to be written.

Give it a unique reference number of its own, so this exact transaction can always be pointed at.

Stamp it with right now, and with the date it stops counting.

Record whose it is, and what kind of movement it was — a purchase, a signup gift, an image generation.

Here it is. Zero minus the amount. That single minus sign is the entire spending mechanism — a spend is just a grant with the sign flipped.

Note which order it relates to, if any.

Write the line. Nothing else in the database changes. Nothing is overwritten.

And when the app needs your balance, it does exactly what you would do with a chequebook stub: adds the lines up.

Whatever the total ends up being is the balance. It was worked out just now and will be thrown away again immediately.

Two Business Decisions Hiding in the Code

Every line has an expiry date — signup credits last a year, purchased credits last until the end of the billing period. And when credits are spent, the lines are read in expiry order, soonest first. Nobody wrote a memo about that; the rule lives in one small phrase, orderBy(asc(credits.expired_at)), and it is as real a piece of company policy as anything in the terms of service.

Five Kinds of Line, One Price List

Everything a credit line can possibly be, and everything a credit can possibly cost, sits in thirteen lines of code.

Here is the complete list of reasons a ledger line can exist — an enum, which means these five are the only options.

A signup gift, a purchase, a manual top-up from support, a test call, and an image generation.

Check Your Understanding

Four money scenarios. These are the ones that cost real money and real trust when you get them wrong.

A customer pays on Stripe's page, then closes the tab before it redirects back to the app. Do they get their credits?

Stripe sends the same "payment complete" message twice. What stops the customer getting double credits?

Scenario

You ask an AI assistant to add a credits feature. It proposes putting a single credits number on the users table and adding to or subtracting from it whenever something happens.

Name what gets worse.

Someone edits the request in their browser to send amount: 1 instead of the real price. What happens?

We have written a lot of rows to a database this module without once asking what a database actually is — or what happens when it disappears. It disappeared. Really. That is Memory and the Outside World.
