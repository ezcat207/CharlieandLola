Who Are You? Sign-In, Sessions, and Trust

How a click on "Sign in with Google" turns into a stamped, tamper-evident wristband your Browser carries everywhere.

Two Very Different Jobs

You can use this app without signing in — you just can't download. Last module we spotted the image route quietly calling getUserUuid() and promised we'd open that box. This is that box.

🎟️

The Gate

Once, you queue up and prove who you are the hard way — passport, booking reference, a good look at your face.

🎫

The Wristband

After that, nobody checks your passport again. Every bar, every stage, every backstage door just glances at the wristband.

⏳

Tamper-Evident, and It Expires

You can't peel it off and hand it to a friend without it showing. And it stops working at the end of the weekend.

The gate is the sign-in flow. The wristband is a session — a signed cookie holding a signed token. "Show me your wristband" is getUserUuid().

💡
Key Insight

Authenticating you is expensive and happens once. Remembering who you are is cheap and happens on every single request. That's different from authorisation, which comes after. Confusing these jobs is where most auth bugs come from — and this app never stores your Google password. It never even sees it.

Here's the clever bit: none of these providers are hard-coded "on". Each one only exists if the matching environment variables are set. The list of sign-in buttons is literally computed from the server's configuration at startup.

If — and only if — all three checks pass, add Google to the list of sign-in buttons users will see.

Every other provider follows this exact same if-it's-configured pattern:

NEXT_PUBLIC_AUTH_GOOGLE_ENABLED Master switch — must literally be "true" or the Google door doesn't exist
AUTH_GOOGLE_ID The public half of this app's Google credentials
AUTH_GOOGLE_SECRET The private half — miss either one and Google never makes it onto the list

Show Me Your Wristband

Every protected action in the app starts with the same question, asked of the same function.

CODE 

export async function getUserUuid() {
  let user_uuid = "";
 
  const token = await getBearerToken();
 
  if (token) {
    // api key
    if (token.startsWith("sk-")) {
      const user_uuid = await getUserUuidByApiKey(token);
 
      return user_uuid || "";
    }
  }
 
  const session = await auth();
  if (session && session.user && session.user.uuid) {
    user_uuid = session.user.uuid;
  }
 
  return user_uuid;
}
PLAIN ENGLISH

Start by assuming this visitor is a guest: an empty id.

Check whether the request came with a bearer token instead of a cookie.

If that token starts with sk-, it's a developer's API key. Look up whose it is and return that.

Otherwise, ask NextAuth for the current server-side session — the signed, verified wristband.

If there's a valid session with a user id, use it.

Hand back whatever was found — a real id, or still just an empty string.

🎫
Being a Guest Isn't an Error

getUserUuid() never throws, never says "unauthorized". It just returns an empty string for a guest. That single design choice is why this app can let logged-out visitors generate images for free — a guest isn't a failure state, it's just another answer.

The Golden Rule

getUserUuid() reads the session on the Server. The Browser sends the cookie; the Server checks its signature before believing a single word of it.

⚠️
The Server Never Takes the Browser's Word

An AI assistant will happily write client-side code that reads session.user.uuid and sends it to the server as a plain parameter. Anyone can open dev tools and rewrite that value to someone else's id before it's sent. Rule: identity comes from the verified session, never from anything the Browser typed into a request. (Cookies can also be marked "secure", meaning they're only ever sent over HTTPS, never plain, unencrypted HTTP.)

A One-Way Blender

Sign-in with a password is one of the doors — but the app never stores the password itself, only a hash.

CODE

          }

PLAIN ENGLISH

If there's no matching user, or they have no password hash on file, stop and return nothing.

Blend the password the visitor just typed and compare fingerprints against the one stored on file.

If the fingerprints don't match, stop and return nothing — the exact same response as "no such user".

You can turn "hunter2" into a fingerprint, but you can't turn the fingerprint back into "hunter2". Notice too: a wrong password and a non-existent account both return the same nothing — the app never tells an attacker which one it was. That's the opposite of storing passwords in plain text, the classic disaster.
