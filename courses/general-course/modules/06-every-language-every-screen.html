Every Language, Every Screen

Add /zh to the address bar and the entire app becomes Chinese — same buttons, same layout, same code. Not one component was duplicated to make that happen.

The Museum Audio Guide

The museum gets built once. The paintings hang where they hang, the corridors run where they run. At the door you pick a language and get a handset — and from then on, every plaque you stand in front of is narrated in your language.

Nobody built a second museum for Mandarin speakers. That is the entire idea of this module, and it has three parts.

🏛️

The Building

The structure — components, layout, buttons, the shape of every page. Built once, shared by everyone.

🎧

The Handset

The locale: which language you picked up at the door. In this app, it is the /zh in the address.

📖

The Narration

The content — every word on the site, living in data files rather than inside the code.

💡
Separate Structure From Content

The moment text stops living inside your components and starts living in data files, you get translations, marketing experiments, and non-developers editing copy — all for free, all at once. It is the same principle as Module 2's "the page is a template, the content is data", now applied to every word on the site. Retro-fitting this later, into an app where text is scattered across two hundred components, is a brutal and expensive job.

The Doorman

One file runs before every single page request in this app. It looks at the address, works out which language you want, and routes you accordingly. It is twelve lines long, and it is the only reason /zh/pricing works at all.

CODE 

import createMiddleware from "next-intl/middleware";
import { routing } from "./i18n/routing";
 
export default createMiddleware(routing);
 
export const config = {
  matcher: [
    "/",
    "/(en|en-US|zh|zh-CN|zh-TW|zh-HK|zh-MO|ja|ko|ru|fr|de|ar|es|it)/:path*",
    "/((?!privacy-policy|terms-of-service|api/|_next|_vercel|.*\\..*).*)",
  ],
};
PLAIN ENGLISH

Borrow a ready-made doorman from a library called next-intl, and the rules we want it to follow.

Make that doorman the thing that greets every visitor. That single line is the whole middleware.

Now describe which addresses the doorman should stand at.

The home page, for one.

And anything that starts with a language code. Notice this list is far longer than the two languages the app actually supports — the doorman recognises thirteen and the museum only narrates in two.

And everything else, except the legal pages, anything under api/, and files like images. That is a regular expression: dense, unreadable, and doing real work.

API addresses are deliberately excluded — a program calling your app does not need a language prefix on its request.

And the actual language list is even shorter and even plainer:

export const locales = ["en", "zh"];

export const defaultLocale = "en";

Two real languages. That is the whole list — adding a third starts here.

What to write in the language switcher menu for each one, in that language.

If we cannot tell what someone wants, assume English.

"As needed" is a small, real product decision: the default language gets the clean address (/pricing), and only other languages carry a prefix (/zh/pricing).

Two Kinds of Text, Two Different Homes

Not all words are the same. This app keeps them in two separate places, and the distinction is worth getting right in any project you build.

🔘

Interface Labels

Buttons, error messages, form hints. Short, reused everywhere. Home: i18n/messages/en.json and zh.json.

📰

Page Content

The entire marketing page, section by section. Home: i18n/pages/landing/en.json and zh.json.

The first kind looks like this — a JSON file of keys and values, where the key is identical in both languages and only the value changes.

🇬🇧

en.json

"sign_in": "Sign In"
"pricing": "Pricing"
"my_credits": "My Credits"

🔑

The Component

Asks for the key, never the words:
t("sign_in")
One component. One line. Both languages.

🇨🇳

zh.json

"sign_in": "登录"
"pricing": "价格"
"my_credits": "我的积分"

The second kind is the surprising one. The entire landing page — hero headline, features, testimonials, FAQ, all eight pricing plans — is a data file, with sections named hero, introduce, benefit, usage, feature, stats, testimonial, faq, cta, footer.

Module 2 showed the page component drawing each section only if the data for it exists. This is where that data comes from.

CODE 

export async function getPage(
  name: string,
  locale: string
): Promise<LandingPage | PricingPage | ShowcasePage> {
  try {
    if (locale === "zh-CN") {
      locale = "zh";
    }
 
    return await import(
      `@/i18n/pages/${name}/${locale.toLowerCase()}.json`
    ).then((module) => module.default);
  } catch (error) {
    console.warn(`Failed to load ${locale}.json, falling back to en.json`);
 
    return await import(`@/i18n/pages/${name}/en.json`).then(
      (module) => module.default
    );
  }
}
PLAIN ENGLISH

Given a page name and a language, go and fetch that page's content.

Treat "Chinese as spoken in mainland China" as plain Chinese — one file serves both.

Build a file path out of the two pieces and load it. landing + zh becomes pages/landing/zh.json.

Hand back whatever was inside. That object is the marketing page — every headline, every feature, every price.

If loading failed for any reason at all, do not crash. Leave a note in the log so someone can find out why later.

Then load the English file instead and hand that back. The visitor gets a page in the wrong language rather than no page at all.

✍️
The Marketing Team Does Not Need You

Rewriting the entire home page means editing a text file. No component is touched, no logic changes, nothing is redeployed differently. When you are designing a new project, ask for this on day one: "user-facing strings go in the translation files, not inline in components." It is one sentence, and it saves weeks.

When There Is No Narration

The same safety net protects the interface labels. Try to load the visitor's language; if anything at all goes wrong, quietly serve English.

CODE 

  try {
    const messages = (await import(`./messages/${locale.toLowerCase()}.json`))
      .default;
    return {
      locale: locale,
      messages: messages,
    };
  } catch (e) {
    return {
      locale: "en",
      messages: (await import(`./messages/en.json`)).default,
    };
  }
PLAIN ENGLISH

Try to load the label file for whatever language this visitor asked for.

If that worked, hand back both the language and its words.

If it failed for any reason — no such file, a typo in the language code, a corrupted file — do not throw an error.

Say the language is English and hand back the English words instead. This is the fallback, and it is the same graceful degradation idea from last module wearing a different costume.

🌏
Localisation Is Adaptation, Not Translation

The Chinese pricing file does not just carry Chinese words — it carries a separate cn_amount, priced for that market, and Chinese checkouts add WeChat Pay and Alipay as payment methods. Words, currency (CNY rather than USD), date formats, payment methods, sometimes whole features. Translating the strings is the easy quarter of the job.

Built From Standard Parts

The building itself is not hand-carved either. The interface comes in three layers, smallest to largest.

1
Tailwind CSS — the raw material

Instead of writing style rules in a separate file, you attach tiny class names directly to the element: flex items-center gap-2 rounded-md. The payoff is that there is never a mystery about which stylesheet a colour came from.

2
components/ui/ — 37 generic parts

Button, card, dialog, tabs, tooltip, table. This is Shadcn UI — and crucially it is not an installed component library. The code was copied into the project, so any of it can be edited. You own the parts.

3
components/blocks/ — whole sections

hero, pricing, faq, footer, showcase. Each one assembled from the generic parts, and each one filled with text from the data files you just met.

A button is not one button. It is a small menu of options, all defined in a single file.

CODE 

      variant: {
        default:
          "bg-primary text-primary-foreground shadow-xs hover:bg-primary/90",
        destructive:
          "bg-destructive text-white shadow-xs hover:bg-destructive/90 focus-visible:ring-destructive/20 dark:focus-visible:ring-destructive/40 dark:bg-destructive/60",
        outline:
          "border bg-background shadow-xs hover:bg-accent hover:text-accent-foreground dark:bg-input/30 dark:border-input dark:hover:bg-input/50",
        secondary:
          "bg-secondary text-secondary-foreground shadow-xs hover:bg-secondary/80",
        ghost:
          "hover:bg-accent hover:text-accent-foreground dark:hover:bg-accent/50",
        link: "text-primary underline-offset-4 hover:underline",
      },
PLAIN ENGLISH

Here is the complete list of looks a button in this app can have. Each one is called a variant.

default — the solid brand-coloured button, slightly dimmer when your mouse is over it.

destructive — red, for the buttons that delete things. Long, because it also describes how it looks in dark mode and when keyboard-focused.

outline — a border and no fill. secondary — quieter than default. ghost — invisible until you hover.

link — looks like a link, behaves like a button.

Every button anywhere on the site is one of these six. That is what people mean by a design system, in practice.

variant="destructive" Every delete button on the site, changed in one place, forever
size="sm" | "lg" | "icon" Three sizes plus the default — so nobody invents a fourth by accident

One Palette, One File

Every colour in the app is defined once, in theme.css, and named after the cartoon it came from.

CODE 

  --cl-yellow: oklch(0.9 0.15 85);
  --cl-orange: oklch(0.8 0.15 60);
  --cl-blue: oklch(0.8 0.08 200);
  --cl-pink: oklch(0.8 0.1 340);
  --cl-green: oklch(0.85 0.15 140);
  --cl-red: oklch(0.7 0.2 25);
  --cl-brown: oklch(0.6 0.1 60);
PLAIN ENGLISH

Seven named colours, each stored in a CSS variable — a name you define once and use everywhere.

The names are the point: --cl-yellow, not #F5D442. Nothing in this app hardcodes a hex code.

oklch is a newer colour notation: lightness, then colourfulness, then hue. Raise the first number and the colour actually looks lighter — which hex codes never let you do.

Dark mode is this exact same list of names, redefined with different values. Nothing else in the app has to know it happened.

🎨
Why "Make the Whole Site More Orange" Is a One-Line Change

Because there is exactly one place a colour is decided, and thirty-seven components that only ever refer to it by name. When you brief an AI assistant on styling, this is the shape to insist on: hardcoded colours scattered through components are how a five-minute rebrand becomes a two-week one.
