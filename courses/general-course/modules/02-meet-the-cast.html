Meet the Cast — How the Code Is Organised

Every file has a job. Once you know the roles, you know exactly where to tell an AI to make a change.

A Codebase Is a Film Production

In Module 1, a message travelled through five different pieces of code — and nobody introduced them. Time to meet the cast, because the single most useful thing you can tell an AI coding assistant is where a change belongs.

🎭

The Cast

The parts you actually see — buttons, upload boxes, preview panels. In code, these are React components living in src/components/blocks/.

🎬

The Crew

They work behind the camera and never appear in the shot: API routes, services, models, and the database. This is where the actual business logic lives.

🪑

Props Department

A shelf of generic, reusable objects any scene can borrow — a chair, a mug, a lamp. In code: 37 small pieces like buttons, cards, and dialogs in src/components/ui/.

🪜

Chain of Command

An actor doesn't wander into the accounts office to rewrite the budget. Requests travel up a strict chain, one step at a time — nobody skips ahead.

When you tell an AI "add a rule that Pro users get 3 free generations a day," it has to put that rule somewhere. Knowing which department owns that rule is often the difference between a codebase that survives a year of changes and one that quietly falls apart before you even deploy it again.

The Map: Who Lives Where

Here's the real top-level folder structure of src/ — annotated with each department's film-crew role.

app/ The stage. Every page and every route — an endpoint — lives here. The folder path IS the address.
components/blocks/ The cast. Big page sections: hero, pricing, faq, footer, imagen-wrapper.
components/ui/ Props department. 37 small generic pieces: button.tsx, card.tsx, dialog.tsx, tabs.tsx.
services/ The crew chiefs. Business rules: credit.ts, order.ts, user.ts, stripe.ts, affiliate.ts.
models/ The records office. The only files allowed to touch the database: user.ts, credit.ts, order.ts, post.ts.
db/ The filing cabinet itself.
schema.ts The schema — table shapes.
index.ts The live connection to the database.
auth/ Security. Who you are — covered in Module 3.
i18n/ Translation department. English and Chinese text — Module 6.
lib/ The toolbox. Small helpers used by everyone: hash.ts, time.ts, resp.ts, storage.ts.
aisdk/ The specialist rig. A hand-built adapter for the Kling video-generation service.

Folders Become Web Addresses

In Next.js — the framework this app runs on — folders under src/app/ literally become the URL path in your browser bar.

[locale]/(default)/pricing/page.tsx becomes charlieandlola.net/en/pricing
api/checkout/route.ts becomes charlieandlola.net/api/checkout
(admin)/admin/orders/page.tsx becomes charlieandlola.net/admin/orders

Two notations make this readable once you know the trick:

[ ]
[locale] — square brackets

Means "anything goes here, and tell me what it was." That's how /en/pricing and /zh/pricing are the same one file.

( )
(default), (admin), (console) — round brackets

Mean "this folder is for organizing only." It does not appear in the URL at all — genuinely confusing the first time you see it.

The Chain of Command, in Three Files

Remember generate-cyberpunk/route.ts from Module 1? Watch how one request passes through three layers, and how each layer only ever talks to the one directly below it.

Layer 1 — The Route

Takes the request, checks in with the Service layer, and replies. File: src/app/api/generate-cyberpunk/route.ts

CODE 

// Get user info
const userUuid = await getUserUuid();
const isRegisteredUser = !!userUuid;
 
// Check credits for registered users
if (isRegisteredUser) {
  const userCredits = await getUserCredits(userUuid);
  if (userCredits.left_credits < CreditsAmount.ImageGeneration) {
    return respErr(`Insufficient credits. You need ${CreditsAmount.ImageGeneration} credits but only have ${userCredits.left_credits}. Please recharge to continue.`, 'INSUFFICIENT_CREDITS');
  }
}
PLAIN ENGLISH

Ask Security who's making this request — their session (Module 3 opens this box).

Turn that into a plain yes/no: are they signed in at all?

If they ARE signed in, check their credits balance before doing anything expensive.

Ask the Model layer how many credits this user actually has left.

Compare it to the price of one image — a number defined in the Service layer, not here.

Not enough? Stop immediately and send back a clear error message.

Layer 2 — The Service

Knows the business rules. File: src/services/credit.ts

CODE 

export enum CreditsAmount {
  NewUserGet = 30,
  PingCost = 1,
  ImageGeneration = 10,
}
PLAIN ENGLISH

Define a fixed, named menu of credit amounts — an enum — used everywhere in the app.

New users start with 30 credits, free.

A test "ping" costs 1 credit.

Generating one image costs 10 credits. Change this ONE number and the whole app updates.

End of the list.

Layer 3 — The Model

The only code allowed to touch the database. File: src/models/credit.ts

CODE 

export async function getAllUserCredits(
  user_uuid: string
): Promise<(typeof credits.$inferSelect)[] | undefined> {
  const data = await db()
    .select()
    .from(credits)
    .where(eq(credits.user_uuid, user_uuid))
    .orderBy(asc(credits.created_at));
 
  return data;
}
PLAIN ENGLISH

A function that takes one input: which user's records to fetch.

TypeScript promises the answer will be a list of credit records, or nothing.

Open a connection to the database — this file is the ONLY one in the whole app allowed to do this.

Ask for rows from the credits table, but only the ones belonging to this one user.

Sort them oldest first, then hand the results back up to the Service layer.

📮
The Route

Takes the incoming request, asks Security who's asking, and asks the Service layer if the rules allow it. Never touches the database directly.

📋
The Service

Owns the business rules — prices, limits, permissions. "10 credits per image" is written down here, and only here.

🗂️
The Model

The only code allowed to run a database query. Every other layer has to ask it — nobody else writes the query themselves.

🗄️
Database

Postgres, accessed through Drizzle ORM. The actual filing cabinet where every credit balance, order, and user record lives.

Click a tab above. Notice each layer only ever talks to the one directly below it — Route never queries the database, Service never touches SQL.

💡
A Rule Should Live in Exactly One Place

Engineers call this separation of concerns. If "10 credits per image" lived in a button instead of the Service layer, you'd end up with the rule in five places — and four of them wrong within a month.

Cast vs Crew: On Stage and Backstage

Some components run on the company's server, before the page even reaches you. Others run in your own browser, on the client side — the line is one piece of text at the top of a file: 'use client'.

🖥️
Server — index.tsx

Looks up the translated text and hands it down. Can read secrets and databases — but can't respond to a click.

🖱️
Client — imagen-client.tsx

Handles clicks, drag-and-drop, spinners — anything that reacts to a human. Never trusted with secrets, because anything in the browser can be read by the user.

Server fetches, client interacts — a hand-off pair from the same feature.

This function runs on the server. It renders before your browser ever sees it.

Lock in which language this request is for.

Fetch all the English/Chinese text for the "imagen" section — a translation namespace.

Bundle that text up as props — ready to pass down to the client component below.

Each piece of on-screen copy gets its own labelled slot.

The Assembled Page

The landing page barely contains content of its own — it's a list of cast members, each handed a slice of data. File: src/app/[locale]/(default)/page.tsx

CODE 

<ImagenWrapper locale={locale} />
{page.introduce && <Feature1 section={page.introduce} />}
{page.benefit && <Feature2 section={page.benefit} />}
{page.usage && <Feature3 section={page.usage} />}
{page.feature && <Feature section={page.feature} />}
{page.showcase && <Showcase section={page.showcase} />}
{page.stats && <Stats section={page.stats} />}
{page.pricing && <Pricing pricing={page.pricing} />}
{page.testimonial && <Testimonial section={page.testimonial} />}
{page.faq && <FAQ section={page.faq} />}
{page.cta && <CTA section={page.cta} />}
PLAIN ENGLISH

Always draw the upload widget — it's always there.

Only draw the "introduce" section if the data file actually has content for it.

Same trick, section by section: benefit, usage, feature, showcase, stats.

…pricing, testimonials, FAQ, and the final call-to-action — each one optional.

The && means "only draw this if there's something to draw." No content, no section — nothing crashes.
